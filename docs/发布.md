# 发布 Siming

在 GitHub Actions 的 **Release** 工作流中选择 `Run workflow`，输入 `1.2.3` 或 `1.2.3-beta.1`。工作流会校验干净工作区和 Tag，统一更新 Cargo、Tauri、C#、Unity 版本，提交 `chore(release): prepare v<version>`，创建 Tag，并构建 GitHub Release。

Release 包含 Windows x64、macOS Intel、macOS Apple Silicon 安装包，以及 Unity `.tgz` 和两个 NuGet `.nupkg`。预发布版本自动标记为 Pre-release；Windows 安装包未签名，macOS 应用使用临时签名（ad-hoc），未经过 Apple 公证。

macOS 在 Tauri 配置中使用 `bundle.macOS.signingIdentity: "-"`，在生成 DMG 前签名完整的 `.app`。CI 和 Release 在构建后运行 `python3 scripts/verify-macos-bundle.py target/release/bundle`，同时校验输出目录中的应用和以只读方式挂载的 DMG 内应用。签名不完整、缺少应用或缺少 DMG 时阻止上传。临时签名验证文件完整性，不代表 Apple 认证的开发者身份，也不能保证 Gatekeeper 允许首次启动。

首次安装 macOS 版本时，将应用拖入“应用程序”后尝试打开；如果系统提示开发者无法验证，可在“系统设置 → 隐私与安全性”中为司命选择“仍要打开”。如果提示“已损坏”，先重新下载最新发布包，检查签名：

```bash
codesign --verify --deep --strict --verbose=2 "/Applications/司命（Siming）.app"
```

签名验证失败时不要继续打开，应报告发布包问题。只有在验证通过且确认安装包来自可信发布后，若系统仍阻止启动，可仅移除此应用的下载隔离标记，再打开：

```bash
xattr -dr com.apple.quarantine "/Applications/司命（Siming）.app"
```

无需关闭系统 Gatekeeper。本机重新构建可执行 `cd apps/desktop && npm ci && npm run tauri -- build`，随后在仓库根目录运行上述校验脚本；DMG 输出到 `target/release/bundle/dmg/`。

Intel macOS 使用 `macos-15-intel` runner。桌面附件仅收集 Windows `.msi` / NSIS `.exe` 和 macOS `.dmg`，不上传 `.app` 目录或内部文件（应用包含在 DMG 内）。安装包附件名添加平台和架构前缀，SDK 保留原包名。创建 Tag 前检查各平台产物和 SDK 包是否齐全、附件名是否重复；上传不覆盖已有同名附件。

Unity 可使用版本固定的 Git URL：

```text
https://github.com/yue19870813/siming.git?path=/sdks/csharp/Packages/dev.siming.sdk#v1.2.3
```

SDK 也可从 Release 下载 `.tgz` 与 `.nupkg`。构建失败时不会创建 Release；版本提交和 Tag 已产生时，应检查日志后修复并重新运行后续构建。

版本准备会同时更新根目录和 `sdks/csharp/tests/RustReference/` 中的 Cargo.lock，仅修改本地工作区包的版本，保留第三方依赖锁定。SDK 的 Rust 参考测试继续使用 `--locked`，错误信息直接输出到 Actions 日志。

若构建失败、版本已写入但 Tag 尚未创建，修复并推送后可在最新 `main` 上再次运行 Release，输入相同版本（例如 `0.1.1`）。版本文件已一致时会复用当前提交，不创建空提交。已有同名 Tag 仍会拒绝发布；不要对旧任务直接重跑来验证新修复，因为旧任务会使用旧代码。

仓库通过 `.gitattributes` 固定文本文件为 LF，保证 Windows 与 macOS 的格式检查一致。前端格式、lint、类型检查、测试，以及 SDK 生成、测试、打包均分别显示为独立步骤。
